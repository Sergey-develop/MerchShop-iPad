# Серверный контур Supabase (подготовка к подключению)

В каталоге находится миграция PostgreSQL и Edge Function `game`. Это отдельный production-контур; локальный демонстрационный адаптер не обеспечивает межустройственной согласованности. До подключения backend и утверждения правил проверки токенов реальную выдачу проводить нельзя. Никакие реальные остатки и вероятности не заданы: все количества и веса равны нулю, активный день не выбран.

## Подключение

1. Создайте Supabase-проект и примените миграцию `migrations/202611190001_game.sql` через Supabase CLI либо SQL Editor. Убедитесь, что расширение pgcrypto установлено в схему `extensions`. Таблицы защищены RLS и не доступны `anon`/`authenticated`.
2. Выполните `supabase functions deploy game --no-verify-jwt` в привязанном проекте. Supabase предоставляет `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` функции автоматически; service role key никогда не добавляется в клиент. Открытые действия функции — только конфигурация, розыгрыш и восстановление по секретному UUID запроса; для администрирования функция сама проверяет JWT через Auth и членство в `game_admins`. Рекомендуется включить ограничения частоты запросов на уровне шлюза перед запуском.
3. Создайте пользователя в Supabase Auth. Доверенный оператор добавляет его UUID в `public.game_admins` через SQL Editor. Для административных действий передавайте `Authorization: Bearer <JWT пользователя>`. Не используйте публичный anon key как токен администратора.
4. Задайте фактические даты, количества, веса и активный день, подключите фотографии и ссылку Telegram. Административные изменения запасов проводите через `game_set_inventory`, а не прямыми SQL-правками: функция блокирует строку и сохраняет балансовое ограничение. День переключается функцией `game_set_active_day`; остатки не переносятся.
5. Согласуйте правила проверки физических токенов и реализуйте их в `validate_game_tokens` с серверной проверкой. Пока `token_validation.mode = unconfigured`, новые розыгрыши отклоняются. Опция `range_only_approved` проверяет только формат и диапазон, **не подтверждает подлинность** и не должна включаться как замена согласованным правилам. Отмена по умолчанию закрыта; допускается только для `reserved` и только при явном включении возврата остатка. Срок действия резерва и отмена уже выданного приза требуют отдельного согласования и реализации.

## Контракт Edge Function

Все запросы — `POST` с JSON `{"action":"..."}`. Публичные:

- `public_config`: Telegram URL и настройки формата (режим `unconfigured` явно означает запрет розыгрыша).
- `draw`: `{action, idempotencyKey, tokens}`. Ключ — случайный UUID v4, созданный **до** отправки и сохранённый клиентом вместе с комбинацией. Повторите с тем же ключом и той же комбинацией при неопределённом исходе. Повтор с другой комбинацией возвращает `IDEMPOTENCY_CONFLICT`.
- `recover`: `{action, idempotencyKey}`. Ключ является секретом доступа к конкретному результату; храните его как чувствительные данные. `NOT_FOUND` при потере сети не доказывает, что параллельный запрос ещё не выполняется; безопасно повторить именно `draw` с прежним ключом и комбинацией.

Ответ `{draw:{id,event_day_id,prize_id,status,created_at,issued_at,prize:{id,name,description,image_url}}}` содержит уже зафиксированный приз. Клиент не генерирует результат и не создаёт новый ключ до завершения сессии. Ошибки: `INVALID_TOKENS`, `TOKEN_RULES_UNCONFIGURED`, `NO_ACTIVE_DAY`, `NO_PRIZES`, `IDEMPOTENCY_CONFLICT` и др. Поле комбинации публично не возвращается.

Администратору доступны `admin_data`, `issue`/`cancel` (`drawId`), `set_inventory` (`inventoryId`, `total`, `weight`), `set_active_day` (`dayId`), `update_day` (`dayId`, `date` или null), `update_prize` (`prizeId`, `name`, `description`, `imageUrl` HTTPS или null, `isActive`) и `set_setting` (`key`, `value`; поддерживаются `telegram_url`, `token_validation`, `cancellation_returns_stock`). Изображение задаётся HTTPS URL; загрузку файла в защищённое хранилище и политику доступа необходимо подключить отдельно. `admin_data` возвращает до 500 последних розыгрышей: для крупных мероприятий нужны пагинация, аудит и регламент хранения персональных/игровых данных.

## Транзакционные гарантии

`game_draw` сериализует повторы запроса advisory-блокировкой, блокирует активный день и строки остатков, выбирает только активные доступные позиции по весам с криптографическим источником PostgreSQL и резервирует единицу в той же транзакции, в которой записывает результат. Повторная выдача отклоняется; подтверждение переводит единицу из резерва в выданное без второго списания. Балансовое ограничение проверяется самой БД. Эти гарантии относятся к одному подключённому PostgreSQL проекту; перед реальным мероприятием обязательно проведите интеграционные испытания параллельных запросов на целевом экземпляре, настройте мониторинг, резервное копирование, права и rate limiting.
